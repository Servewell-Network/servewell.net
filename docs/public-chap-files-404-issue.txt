Eventually, I got this:

Yes, your assets SHOULD be served without touching your Worker code — and they are, most of the time. Here's the exact flow for a request like https://servewell.net/-/Genesis/1:

Request comes in → not in run_worker_first list → skip Worker
Assets system looks for a matching file → found → served directly ✅
But if the asset is not found → since you have a Worker script present, the request falls through to your Worker code
Your Worker returns a hardcoded 404 instead of env.ASSETS.fetch(request)
The real question is: why would a deployed asset suddenly not be found? This is the intermittent part. There are two likely causes:

Cause 1: Your not_found_handling: "none" + missing fallback
With not_found_handling: "none", when the assets layer can't find a file, it falls through to your Worker. Your Worker then returns a hardcoded 404. But if you used env.ASSETS.fetch(request) as the fallback, it would get a second chance to find the asset.

Cause 2: The global_fetch_strictly_public compatibility flag
You have "global_fetch_strictly_public" in your compatibility flags. This flag changes how fetch() behaves — it restricts subrequests to only publicly accessible resources. This could be interfering with how the assets binding resolves internally, especially as edge nodes propagate and cache state changes.

Recommended fixes (in order of impact):
1. Add env.ASSETS.fetch(request) as your fallback (highest impact):

// Instead of:
return new Response("Not Found", { status: 404 });

// Use:
return env.ASSETS.fetch(request);
2. Remove global_fetch_strictly_public from your compatibility flags unless you have a specific reason for it. This flag is not commonly needed and could be interfering with asset resolution.

3. Consider setting not_found_handling to "404-page" and adding a 404.html to your assets directory. This keeps the assets layer handling 404s entirely, without ever invoking your Worker for missing assets.

4. Your compatibility_date of 2025-07-02 means you already have the assets_navigation_prefers_asset_serving behavior — this is good, it means browser navigation requests prefer asset serving. But it doesn't help with non-navigation requests (like fetch() calls from client-side JS).

    3. Manual: scripts/cf-redeploy.sh (npm run cf-redeploy) for immediate recovery from terminal.
  All recovery attempts are logged to a RECOVERY_LOG KV namespace (first 5 + last 5 entries).
  Log is readable/clearable via GET/DELETE /api/recovery-log (moderator auth required).
